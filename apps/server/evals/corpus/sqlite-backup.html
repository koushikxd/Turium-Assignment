Backing up a live SQLite database safely

SQLite stores a whole database in a single file, which makes it tempting to back it up with cp. On a database that nothing is writing to, that works. On a live database it can quietly give you a corrupt copy, and you will only find out on the day you need it.

Why copying the file is not enough

A copy made while a transaction is in progress can capture half of a change. In WAL mode it is worse: recent committed transactions live in the separate -wal file until a checkpoint moves them into the main file. Copy only the main file and you lose them; copy both files at slightly different moments and they may not match each other. The file copy has no idea what a transaction is.

Option one: VACUUM INTO

Since SQLite 3.27, the statement VACUUM INTO followed by a file name writes a complete, consistent copy of the database to a new file. It runs as a single read transaction, so writers can continue while it runs in WAL mode, and the result is also compacted, with no free pages. The target file must not already exist. For most small applications this is the simplest correct backup: run it from a scheduled job, then move the new file somewhere else.

Option two: the online backup API

The backup API copies the database page by page into another database connection. It can copy in small steps, releasing locks between them, which matters for large databases on busy systems. The sqlite3 command line shell exposes it as the .backup command, and most language drivers expose it too. If another connection writes to the source in the middle of a backup, the backup restarts automatically, so on a database with constant writes it may take a while to finish.

Check what you made

A backup you have never restored is a hope, not a backup. After every run, open the copy and run PRAGMA integrity_check; it should return a single row saying ok. Once a month, restore the latest backup into a scratch environment and start the application against it.

Keep more than one

Keep a week of daily copies and a few months of weekly ones, and store at least one copy on a different machine. A backup that sits on the same disk as the database protects you from mistakes but not from the disk failing.
